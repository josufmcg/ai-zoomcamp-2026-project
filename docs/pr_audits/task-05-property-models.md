## Reviewer notes and verdict

**Verdict: CHANGES REQUESTED (then approved).**

**Finding 1 — downgrade would fail on PostgreSQL.** The autogenerated migration
created `UnitType` as a native PostgreSQL enum but did not drop it in
`downgrade()`, so `alembic downgrade base` raised
`type "unitenum" does not exist` after the table was gone. The model's SQLite
unit tests never caught this because SQLite stores the enum as a `VARCHAR` +
`CHECK` and has no `DROP TYPE`.

**Finding 2 — duplicated `CHECK` constraint.** Autogenerate emitted the SQLite
`CheckConstraint` twice in the same `create_table`, which would create a
redundant, unnamed constraint.

**Fix applied by the human reviewer.** The migration was rewritten by hand in
the established style: a single `sa.CheckConstraint` and an explicit
`sa.Enum(...).drop(op.get_bind(), checkfirst=True)` in `downgrade()`. This was
turned into a standing rule in `AGENTS.md`: *"Write new Alembic migrations by
hand in the established style (explicit enum `drop()` in `downgrade`);
autogenerate emits SQLite `CHECK` constraints twice."*

**Evidence used to accept.** Round-tripped `alembic upgrade head` and
`alembic downgrade base` against **both** in-memory SQLite and the live Docker
Compose PostgreSQL, and confirmed `alembic revision --autogenerate` reported no
remaining drift.
