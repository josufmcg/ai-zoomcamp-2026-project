# Completed PR audits

The evaluation criteria ask for **PR audit output**, not only an audit template.
`.github/pull_request_template.md` is the blank checklist that GitHub shows on
every new pull request; this directory holds examples of that checklist
**actually applied** to a change, so a reviewer can see the audit in practice.

Each file is a completed copy of the template for one AI-assisted task: the same
section headings, the boxes ticked, the reviewer's own notes, and — most
importantly — the **outcome of the independent checks**. Two of the examples end
in a "changes requested" verdict where the human review caught a real defect the
model's passing tests had missed, because that is what an audit is for.

| Audit | Task | Verdict | What the review caught |
| --- | --- | --- | --- |
| [`task-05-property-models.md`](task-05-property-models.md) | 5 — property hierarchy models | Changes requested | The autogenerated migration would not downgrade on PostgreSQL (enum not dropped); the SQLite `CHECK` was emitted twice. |
| [`task-08-property-endpoints.md`](task-08-property-endpoints.md) | 8 — property and tag endpoints | Changes requested | A resident-scoped query written as a bare `.any()` returned every row, leaking other residents' data. |

## How these relate to the rest of the documentation

- `docs/ai_policy.md` section 5 requires the checklist to be worked through
  before a change is accepted; these files are the concrete result.
- `docs/ai_workflow.md` section 3 records the same tasks as
  prompt → result → correction; the audits here are the *review* half of that
  record, exercised end to end.
- The defects caught here are written up by symptom, evidence, root cause, and
  fix in `docs/operations.md`.

The blank template stays the single source of truth for the *sections* a review
must contain; if a section is added there, add it to these completed examples
too. `backend/tests/test_security_artifacts.py` keeps the template, these
audits, and the operations notes in shape.
